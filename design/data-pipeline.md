# Data pipeline

Everything in `data/` that the server reads is generated by the scripts in `backend/scripts/` and committed. You only need this page if you change the word lists, the filters, the blocklists, the schedule or the clues. For why the lists and clues are built this way, see [ADR 0002](adr/0002-word-lists-from-concreteness-ratings.md) and [ADR 0006](adr/0006-clues-from-local-models-grounded-in-wordnet.md).

## Setup

Install the script dependencies and WordNet:

```bash
pip install -r requirements-scripts.txt
python -m nltk.downloader wordnet
```

You also need two inputs that are not committed:

- `data/glove.6B.300d.txt`: GloVe 6B 300d vectors (about 1 GB), from the [Stanford GloVe project](https://nlp.stanford.edu/projects/glove/).
- `data/raw/concreteness_ratings.csv`: the Brysbaert et al. concreteness ratings (1.6 MB), from the [Hugging Face mirror](https://huggingface.co/datasets/StephanAkkerman/concreteness-ratings) ([original on OSF](https://osf.io/kj76e/)). Its columns used here are `Conc.M` (concreteness, 1–5), `Percent_known`, `SUBTLEX` (subtitle frequency) and `Dom_Pos` (usual part of speech).

## Word lists and embeddings

From the repository root:

```bash
python backend/scripts/build_word_lists.py
python backend/scripts/extract_embeddings.py
```

`build_word_lists.py` prints how many words each filter removed and writes:

| File | What's in it | Rule |
| ---- | ------------ | ---- |
| `data/guess_words.txt` | Words you can guess (~31,000) | Every single word in the dataset with a GloVe vector that isn't a proper noun |
| `data/target_words.txt` | The answers (~200) | The hand-picked words in `data/answer_list.txt`, checked: each must be a guess word, not in `data/target_blocklist.txt` and not a plural of another answer ([ADR 0009](adr/0009-hand-picked-answer-list.md)) |
| `data/raw/answer_candidates.txt` | More possible answers (git-ignored) | Nouns known by ≥ 95% of raters, concreteness ≥ 4.0, subtitle frequency ≥ 50, no plurals, not blocked and not answers yet |
| `data/hint_words.txt` | Words a Hint may reveal (~16,700) | Known by ≥ 95%, subtitle frequency ≥ 10, not an inflected form of another word |
| `data/word_forms.txt` | Plurals, verb forms, comparatives and British spellings (~24,000) | Forms that aren't guess words themselves, each mapped to a base word: the rules in `backend/utils/word_forms.py`, WordNet's lists of irregular forms ("larvae", "blew"), and British spellings from the narrow rewrite rules and table in `build_word_lists.py` ("colour", "centres") |
| `data/irregular_plurals.txt` | Irregular plurals (~225) | From WordNet ("larvae" → "larva"), kept even when the plural is a guess word itself, so it wins when the singular is the answer |

Names are left out of the word forms too. The thresholds are constants at the top of `build_word_lists.py`. A word counts as a proper noun when WordNet only knows it with a capital letter, or when it's listed in `data/proper_nouns.txt`.

`extract_embeddings.py` looks up a 300-dimensional GloVe vector for every guess word, scales each to unit length and saves them as float16 in `data/embeddings.npz` (about 18 MB).

**Common edits:**

- **Change the answers:** edit `data/answer_list.txt` (one word per line; anything after a `#` is a comment), rerun `build_word_lists.py`, then `build_schedule.py`. The build stops and names any word that fails a check. New answers need clues too: run `generate_clues.py` (it skips words already in the report), then `--export-only`.
- **Keep a word from ever being an answer:** add it to `data/target_blocklist.txt`.
- **Ban a proper noun that slipped through:** add it to `data/proper_nouns.txt` and rerun `build_word_lists.py`.

## Daily schedule

```bash
python backend/scripts/build_schedule.py
```

It shuffles the answers into `data/daily_schedule.txt`, where line N is puzzle #N and puzzle #1 is `LAUNCH_DATE` in `backend/config.py`. Each line is an HMAC of the word, so it needs the schedule key (`WORDHUNT_SCHEDULE_KEY` or `schedule.key`).

Rerunning it never changes today's or earlier puzzles. It drops future words that are no longer answers and appends new ones, and no word repeats. Changing `LAUNCH_DATE` or deleting the file would change puzzles people have already played.

There's one puzzle per answer, so the schedule runs out after as many days as there are answers: with today's 200, the last puzzle is on 2027-06-10. After that, `/today` gives no puzzle and the page offers only past ones, so add answers (and their clues) well before then.

A relaunch, which starts again at puzzle #1, is a one-off decision (ADR 0003; done on 2026-11-23). Set `LAUNCH_DATE` to the launch day, empty `data/daily_schedule.txt`, rerun the script with the **same key** and rerun `generate_clues.py --export-only`. Clues are keyed by word and key, not by puzzle number, so the clues file comes out the same. Browsers move saves from the old launch aside by themselves (ADR 0004). If the results table already has rows, empty it, because a device's first result for a puzzle number wins.

For your own fork, make a new key and a separate schedule file:

```bash
WORDHUNT_SCHEDULE_PATH=data/my_schedule.txt python backend/scripts/build_schedule.py --new-key
```

`--new-key` creates `schedule.key` only when no key is set. Keep a copy of it somewhere safe: without it the schedule and the clues can't be read.

## Clues

`generate_clues.py` writes three clues per answer with a local [Ollama](https://ollama.com) model (`qwen3.5:4b`) and checks them with a second one (`gemma4:e2b`). Pull both first:

```bash
ollama pull qwen3.5:4b
ollama pull gemma4:e2b
python backend/scripts/generate_clues.py
```

**How a clue set is made:**

- **The meaning.** The writer isn't asked to recall facts. It gets one dictionary meaning from WordNet: of the word's senses, the one closest to the word's 25 nearest neighbours in the game's embeddings, so the clues describe the meaning the ranks are built on (`crane` the bird or the machine, whichever the embeddings favour). The most common sense wins unless another is clearly closer, and senses that are names, or whose definitions contain one, are skipped.
- **The vague clue** comes from WordNet, not the model: the meaning's broader category, such as "A kind of wading bird". Categories that cover too few things, are too abstract, or aren't everyday words (checked against the concreteness ratings, so the CSV is needed) are skipped. About 97% of answers get one; for the rest the model writes the vague clue too.
- **The other clues.** The writer fills in the meaning in its own words and the strong clue first, then the medium clue, which should restate a detail the dictionary meaning gives.

**Each set must pass three checks:**

- **Rules:** no answer word or a word built from it, nothing about letters, spelling or sounds, no names.
- **Facts:** the second model, also given the meaning, checks the model-written clues for errors. It catches only some subtly wrong clues.
- **Solver:** the second model guesses the word from the clues, one more clue at a time, and its guesses are ranked like a player's. The strongest clue must bring it into the top 10, and none of its three guesses from the vague clue alone may be the answer. If a WordNet category gives the word away, the next broader one is tried.

When a set fails, the writer is told exactly what went wrong and asked to fix it, up to 4 tries in all (`--attempts`).

**Running it:**

- On a 50-word test set of non-answers (2026-11-21), 45 sets passed. Of 20 hand-labelled passing medium clues, 15 were correct, 4 doubtful and 1 wrong; the fact checker catches only about a quarter of wrong clues. **Skim the report before using the clues.** Sets marked `review_first` (the medium clue shares no word with the dictionary meaning) are the likeliest to hold an invented detail, so read those first.
- On a CPU it takes about 45 seconds per word: the run for the 200 answers took about 2.5 hours.
- Each request asks Ollama for an 8,192-token context (`NUM_CTX`). Ollama's default is the model's maximum, which made the writer hold about 12 GB of RAM. A prompt that would nearly fill the context is an error for that word, never a silent cut.
- Progress goes to `data/raw/clue_report.json` after every word (git-ignored, since it names the words), written to a temporary file and then moved into place, so Ctrl+C or a kill never damages it. Rerun the same command to carry on: only unfinished words are done. A one-line summary per word goes to `data/raw/clue_report.log`; the screen shows only counts, never words.
- A word whose models fail (Ollama down, timeouts, malformed replies) is logged and tried again on the next run; after 3 in a row the run stops.
- `--redo-failed` retries the words that failed. Each round uses a new sampling seed (the report records the word's `round`), because with the same seed a retry repeats nearly the same tries: on the answers, a same-seed retry rescued 1 of 22. `--words <file> --report <file>` runs on another word list, such as a test set, without touching the answers. `--summary` prints the pass rate, failure reasons and time, naming no words.
- **A run never writes `data/clues.json`.** After the skim, `--export-only` writes every answer's full clue set, including sets that failed a check (see ADR 0006 for the trade-off); only a word whose models never finished, and words from other lists, are left out. Skim the failed sets (`"passed": false`) and the `review_first` sets first. The file is keyed by clue codes, which the schedule doesn't use, and sorted by them, so it doesn't tell which day a set is for (ADR 0003). That step needs the schedule key, and refuses to write the file if the key doesn't decode `data/daily_schedule.txt` or the report has no finished sets. A scheduled puzzle never loses clues it already has.
- Puzzles without clues still work: the help ladder goes straight to hints.
